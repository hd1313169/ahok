## Context

See proposal.md - Why. Two static artifacts are in scope:
- `briefing.html`: a single-file slide deck (JS-driven `.slide` sections, most visual weight already carried by existing CSS component classes like `.card`, `.criteria-grid`, `.qa-card`).
- `prototype/*.html`: 13 independent static screens sharing `styles.css` / `demo-nav.js`. Per PRODUCT.md, screens do not share data — form fields (e.g. `11-edit-med.html`'s "儲存") do not persist or sync to other screens. There is no backend.

Both are pitch/demo artifacts only (per the user's explicit scope: a 7-minute proposal presentation, not a functioning PoC).

## Goals / Non-Goals

**Goals:**
- Rewrite the Proposal slide's core hypothesis and add an evidence slide, reusing the deck's existing visual language rather than inventing new components.
- Add a plain-language purpose caption (primary) and an optional color/icon accent (secondary) to the elder-facing and family-facing prototype screens listed in proposal.md, demonstrable in a live 7-minute walkthrough.
- Keep the recognition feature scoped to "what's this dose loosely for, and does it match what my family already set up" — no medication database, no clinical fields, no photo-comparison step — consistent with the earlier "don't build a maintained medication record" decision.

**Non-Goals:**
- No real photo capture, upload, storage, or backend — the caption/color fields in the family form are static demo inputs, matching the existing precedent that "儲存" does not persist (PRODUCT.md).
- No photo-of-the-dispensing-pack feature at all (superseded — see Decision 1): recognition is not a visual matching/comparison task the elder performs.
- No cross-screen data binding beyond what already exists (screens remain independently authored static HTML).
- No drug-interaction checking, dosage validation, or any clinical decision logic.
- No changes to the escalation-notification mechanism, PoC validation metrics, or recruitment flow — all confirmed out of scope for this pitch.

## Decisions

1. **Recognition splits into two different problems — only one is still unsolved once family pre-sorts doses.** Label-comprehension failure (not being able to read a raw dispensing bag's printed instructions) is largely already resolved by the existing "family pre-sorts doses into a time-slot pack" mechanism — by the time a dose reaches the elder, the compartment/pack already answers "which one, now." What survives that pre-sorting is a separate problem: not being able to say what a dose is for, even when it's taken correctly and on time. That's a comprehension/reassurance gap, not a mis-identification risk. *Consequence:* the recognition feature is not a photo-vs-physical-object comparison the elder performs (that would reopen a verification step the "single-step confirm" acceptance criterion forbids) — it's a plain-language purpose caption, addressing the comprehension gap directly. *Alternative considered:* photograph the dispensing pack so the elder can visually match it — rejected because pre-sorting already solves the identification problem the photo would target, making it redundant work that risks turning "confirm" into a two-step "compare, then confirm."

2. **Optional color/icon accent mirrors the family's existing physical pillbox coding — it is not a second identification system.** Many families already color-code or label their physical pillbox compartments. When set, the app reuses that same color/icon per time slot purely as a visual echo between screen and physical object, lowering the friction of switching attention between the two — it is not presented as something the elder must check against anything. It carries no meaning on its own and is never required to complete the confirm flow. *Alternative considered:* an app-defined color/icon scheme (e.g. a fixed palette per meal) — rejected because a scheme the elder didn't already recognize would be one more thing to learn, conflicting with the "reuse familiar habits" acceptance criterion.

   **Where the accent lives (revised):** the accent recolors the medication icon badge itself (the circle behind the pill glyph), not a separate marker next to the caption text. First pass added a small standalone `.accent-dot` next to the caption, specifically to avoid the badge because on `03-medlist.html` the badge's color also does double duty as a weak secondary status signal (done/pending/future). On reflection that concern doesn't hold up: the status tag next to each row already independently and completely triple-codes status (its own background color + icon + text, e.g. a solid dark-green "吃過了" pill), so the badge's color was always a *redundant* second copy of that signal, not the sole carrier of it. Freeing the badge to show the accent instead, and letting the status tag alone carry status, loses no accessibility coverage and puts the accent where the eye already looks (a 56px badge is far more legible than a 10px dot) — directly answering user feedback that the dot was too easy to miss. Concretely: sun reuses the existing `.card__icon--warm` tint, pine reuses the existing `.card__icon--muted` tint, and earth needs one new `.card__icon--earth` tint; the standalone `.accent-dot` classes are removed. On `01-today.html` specifically there is no status competing for the badge at all (it only ever shows the single "action needed now" card), so this was always safe there and produces no visible change for the current demo data (morning = sun = already the existing warm tint).

3. **Static demo values, not a working input flow.** The prototype has no backend and existing forms already don't persist. The family form's caption and color/icon fields are decorative inputs consistent with its other fields; the elder-facing screens use fixed demo values. *Alternative considered:* localStorage-backed persistence so the demo "actually works" — rejected as unneeded complexity that doesn't change what the pitch needs to show.

4. **Evidence slide reuses the deck's existing stat/card visual grammar** (the pattern already used in `criteria-grid` / `qa-card`), placed immediately after the Proposal slide and before the Persona slides — anecdote, then data proof, then persona detail. Source attribution is a small caption per statistic, using the same abbreviated citation style already used in the underlying research notes (e.g. "pmc.ncbi.nlm.nih"), not full academic citations — appropriate for a pitch deck.

   **Concrete layout:** four stat cards in two labeled groups ("這不是個案": 32.1%~35.4% + 19.6%; "而且常常是「看不懂」造成的": 43.3% + 40.0%), not a flat grid, so the slide argues rather than just lists. The second group's numbers are deliberately echoed later on the Insights & Decisions slide's two-layer breakdown (Decision 1) rather than explained here — this slide raises the numbers, that slide pays them off.
   - **Groups sit side by side, and each group's own 2 cards sit side by side too — all 4 cards end up in one horizontal row.** First pass stacked the two groups vertically; second pass put the groups side by side but stacked each group's 2 cards vertically inside it, which left wide, mostly-empty cards (short stat/label/source content in a half-slide-wide box) — user feedback on that rendered result, again too much whitespace. Reverted `.evidence-grid` to 2 columns (its original setting) while keeping `.evidence-blocks` at 2 columns, so each group's pair sits side by side under its own bar and the whole slide reads as 4 narrower, content-fitted cards in one row (two bars above marking which pair belongs to which group). Groups collapse to a stacked column under 760px; within a group, its 2 cards additionally collapse to 1 column only under 480px (phone-width fallback).
   - **Third pass: back to a true 2×2 card grid, with substantially larger text.** User asked directly for a 2×2 grid with bigger numbers/labels rather than a single row of 4. `.evidence-blocks` is stacked vertically again (each group full-width, its own bar above its own 2 side-by-side cards), so group 1's pair forms row 1 and group 2's pair forms row 2 — a literal 2-column/2-row arrangement of the 4 cards. This time the earlier "too much whitespace" risk is addressed at the source rather than by shrinking the layout: `evidence-stat` grew from `clamp(32px,4vw,46px)` to `clamp(44px,6.5vw,72px)`, `evidence-label` from `clamp(16px,1.3vw,18px)` to `clamp(19px,1.9vw,24px)`, card/group padding increased to match — bigger content fills the bigger cards instead of leaving them empty. `.evidence-blocks` also got `flex:1` + `justify-content:space-evenly` (the same technique used for the Proposal sheet) so the two rows fill the slide's available height evenly instead of leaving a dead zone below.
   - **Fourth pass: removed the group/bar background fills.** User asked to remove both the black bar background and the group's tinted background, and make the bar text black and left-aligned instead of centered white-on-black. `.evidence-group` no longer sets `background` (was `var(--primary-tint)`); `.evidence-group .bar` overrides the shared `.bar` class's `background:var(--bar-black); color:#fff; text-align:center; padding:14px 16px;` down to `background:transparent; color:var(--ink); text-align:left; padding:0; margin-bottom:8px`. Scoped to `.evidence-group .bar` specifically — the base `.bar` class is used elsewhere in the deck (e.g. JTBD) and must keep its filled black-bar look there; only the Evidence slide's usage changes. The 4 stat cards keep their own white `.card` background/shadow/border, so the numbers still sit in a visible box — only the shared tint *behind* the bar+cards and the bar's own fill are gone.
   - **Fifth pass: dropped the group's inset padding so the bar and cards share a left edge.** The `clamp(18px,2.6vw,28px)` padding on `.evidence-group .evidence-grid` was there to inset content from the (now-removed) tinted background's edge; with no background left to inset from, it just left the cards indented relative to the now-flush-left bar text. Removed the rule entirely — the bar's left edge and the first card's left edge now align.
   - The family-reliance statistics (65% / 79%) are deliberately left off this slide — they support the family-side design decisions, not the problem-scale argument this slide is making, and adding a 5th/6th card would blur the two-group structure.
   - Card style: large numeral reusing the deck's existing big-stat treatment (the weight/size already used for `.summary-rollup__stat`), short label, small source citation — framed in the existing `criteria-grid` card shell rather than a new component.

5. **Caption content stays plain-language by convention, not validation.** The purpose-caption field's label/placeholder guides family toward a plain description (e.g. "顧心臟的藥") rather than a drug name or diagnosis. Since the prototype has no backend, this is enforced by field design, not runtime validation — consistent with how the rest of the prototype has no input validation.

6. **The underlying research notes are never named as a source in audience-facing content.** Statistics and the Decision-1 reasoning belong on the evidence slide and the Insights & Decisions slide, cited only via the same abbreviated source style already in use (e.g. "pmc.ncbi.nlm.nih", census/moi.gov attribution for the language statistic) — the internal research notes file itself is not a public document and must not be named or shown as a citation in briefing.html.

7. **Group visually related content with a shared container ("common region"), not uniform gap spacing alone.** User feedback on the rendered Evidence and Proposal slides: colors are fine, but every direct child of `.slide` (bar, meta line, card grids) currently shares one `.slide`-level gap, so nothing signals which elements belong together versus which start a new group — a pure-proximity layout, which reads as a flat pile rather than organized sections.
   - **Evidence slide:** wrap each row's `.bar` + `.evidence-grid` pair in a new `.evidence-group` container (bar flush against the container's top edge, no gap — like a header strip on a body; the grid gets internal padding). Use a small gap between the bar and its own grid, and a distinctly larger gap between the two `.evidence-group` containers, so proximity itself now reinforces the grouping instead of contradicting it.
   - **Proposal slide:** the slide's own eyebrow calls it "一頁提案" (a one-page proposal) — it should read as one document, not six independently-shadowed floating cards of equal weight. Wrap `.proposal-meta` and all six numbered items in one shared bordered/shadowed `.proposal-sheet` frame; the six items become internal rows separated by thin dividers rather than each keeping its own card shadow/background, except the core-hypothesis row, which keeps its existing accent-tinted background as the one emphasized element inside the sheet. Result: two-level hierarchy (the sheet as a whole, and the one highlighted line inside it) instead of six same-weight cards competing for attention.
     - **Follow-up (even vertical distribution):** the sheet's height was originally just its content's natural size, leaving a block of dead space below it on taller viewports (all 6 rows packed at the top) — user feedback asked for even distribution instead. Made `.proposal-sheet` `flex:1` (so it grows to fill the slide's remaining vertical space after `.slide-head`) plus `display:flex;flex-direction:column;justify-content:space-evenly`, so its 4 direct children (meta, two-col row, core row, three-col row) spread evenly across whatever height is available rather than clustering at the top. The divider rule (`> * + *`) keeps its border-top but drops its own `margin-top` (the flex `gap` now supplies the guaranteed minimum spacing; `justify-content` distributes any leftover).
   - *Alternative considered:* just increasing the existing uniform gap value — rejected because proximity alone is a weaker grouping signal than a shared container (common region), and a bigger uniform gap would still leave the bar/meta line looking disconnected from its own content, not fix the actual complaint.
   - Scope note: this pattern (shared container > uniform gap for grouping) is confirmed for the Evidence and Proposal slides specifically; extending it to other slides (e.g. Design Goal's `criteria-grid`) is a follow-up, not yet requested.

8. **Insights & Decisions is split into 5 single-topic slides and relocated to sit immediately after the Evidence slide, live-narrated ones first.** User feedback: the original single slide crammed 5 distinct sub-points into 2 dense QA cards (Q1: language, gamification; Q2: recognition-scope, family-exceptions, no-calendar) — "混雜，很難讓人短時間內看懂." It was also the deck's last slide, so presenting it live meant scrolling past 5 un-narrated slides (Persona×2, JTBD, Design Goal, Design Guide, IA) first.
   - New order: Cover, Proposal, Evidence, then 5 single-topic slides, then Persona×2 / JTBD / Design Goal / Design Guide / IA (unchanged relative order, just pushed later).
   - Within the 5: **3 live-narrated slides first** (language-differentiation, recognition-scope, family-photo-over-gamification), **2 backup slides after** (family-exceptions-only, no-calendar) — so the live path (Cover → Proposal → Evidence → 3 insight slides → switch to the separate demo app) is fully contiguous with nothing to scroll past, while the backup pair stays reachable immediately afterward for Q&A rather than all the way at the deck's original end.
   - Each split-out slide keeps a small eyebrow tag naming which competition rubric question it answers (Q1 or Q2) plus the original question text in small print, so a judge reading the full deck later can still see the Q1/Q2 structure despite the content being split across slides — splitting must not break that traceability.
   - Content itself is unchanged from the original QA card wording (already rewritten earlier in this change for Q1's language point and Q2's recognition point) — this decision is about slide *structure and placement*, not new wording, except for the newly-promoted family-photo slide (see Decision 9).


9a. **The cover slide's section-jump navigation (`.cover-steps`) is removed, not just re-indexed.** It had already needed re-deriving twice (once when the Evidence slide was inserted, again for the 14-slide Insights & Decisions split), and the user asked directly to remove it rather than keep maintaining it. Removed the `.cover-steps`/`.cover-step` HTML block, its CSS, and the JS click-listener that wired `data-target` to `goTo()` — `prevBtn`/`nextBtn`/arrow-key navigation (which don't depend on hardcoded indices) are untouched. Net effect: one less thing to re-derive on every future slide-count change.

9. **A third live insight is added: rejecting gamification in favor of a family-photo unlock — chosen because it already has a zero-cost demo pairing.** The two backup-turned-candidates were family-exceptions-only (already fully demonstrated by the 05-family-overview screen in the demo — narrating it too on a slide would just repeat what the demo already shows) and no-calendar (about appointment reminders, which sit outside poc.md's medication-focused P0 scope and would loosen the live narrative's focus). The family-photo point avoids both problems: `02-confirmed.html` already displays a real family photo on the confirmation badge (via `family-photo.js`, localStorage-backed, `img/success.jpg` as the demo default) — that screen is already a step in the existing demo sequence (08→01→**02**→11→05), so promoting this insight to a live slide costs zero extra demo screens or clicks, only a sentence of narration when the presenter reaches 02-confirmed. It also rounds out the 3 live insights into 3 distinct UX dimensions rather than 2 similar ones: accessibility (language), information/cognitive design (recognition), and emotional/motivational design (family photo) — a more complete design-thinking narrative for a UX/UI competition. Content for this slide is unchanged from the existing Q1 "遊戲化獎勵機制" QA point wording; unlike the language and recognition insights, it cites no external statistic — it is disclosed as coming from direct personal/family observation, not desk research, consistent with how the language insight already distinguishes its primary-research origin from poc.md's secondary data.

10. **Cover and Proposal drop 回診 (appointment reminder) language; Design Goal's one-line summary does too — IA and demo-nav labels do not.** The live 7-minute pitch never mentions 回診 (established earlier: it's outside poc.md's medication-focused P0 scope). The cover headline "吃藥不漏、回診不忘" and the Proposal slide (also live-narrated) still promised it, which a judge would notice within the first slide as a mismatch between what's promised and what's actually presented.
    - **New tagline: "記得清、看得懂、按得到"** (remember clearly, understand it, be able to press it) — replaces "吃藥不漏、回診不忘" as the cover `<h1>`. Maps directly onto the product's actual reminder → recognition → confirm flow, keeps the same short parallel-clause rhythm as the original, and introduces no new claim the deck doesn't back up.
    - **Cover subtitle**: drop "／回診提醒" from "服藥／回診提醒 App" → "服藥提醒 App".
    - **Proposal slide** (live): `proposal-meta`'s "服藥回診提醒 App" → "服藥提醒 App"; 問題描述 drops "回診日期也記不清楚" and gains a clause reinforcing the comprehension problem instead (ties to the evidence slide's 40% stat) — "陳奶奶每天要吃 5 種藥，常想不起來吃了沒，也說不清楚自己在吃什麼。兒子只有假日回家，平日沒辦法隨時確認。"; 成功指標's "清楚記得回診時間" → "看得懂在吃什麼" (echoes the new tagline's second clause).
    - **Design Goal's `goal-statement`** (backup slide, but a single-sentence summary carrying the same weight as the cover headline): drops "準時回診" — "...也能記得清、看得懂、按得到，並讓忙碌的子女放心" — echoes the new tagline directly so the deck's two "headline-weight" statements (cover + Design Goal) stay in sync even though Design Goal itself is backup-only.
    - **Deliberately NOT changed:** the IA architecture slide's screen inventory (回診提醒, 編輯回診 — these screens genuinely exist in the 13-screen prototype) and the demo-nav menu's link labels for those same screens. Removing 回診 there would misrepresent what the prototype actually contains — "not part of this pitch's live narrative" is a different claim from "doesn't exist," and only the first is true.
    - **Deliberately left alone for now:** Persona (陳奶奶/陳阿明) goal/challenge lists and the JTBD slide's dedicated 回診 row — these are backup detail slides that are expected to carry more scope than the compressed live pitch (an appendix being more thorough than the headline is normal, not an inconsistency). Revisiting these is a separate, not-yet-requested follow-up if the user wants the whole deck scrubbed rather than just its headline-weight statements.

11. **The 5 insight slides drop their Q1/Q2 rubric tags for unified sequential numbering.** User asked to replace each slide's eyebrow tag ("洞察 Q1 · 研究與探索的洞察" etc.) with a single running count instead — "洞察 1", "洞察 2", ... "洞察 5" — across all 5 slides regardless of which original competition-rubric question they trace back to. The verbose original rubric question text (`.insight-question`, small italic print under the eyebrow) is removed along with it — it existed specifically to preserve Q1/Q2 traceability for a judge reading the full deck (Decision 8's original rationale), which no longer applies once the tag itself no longer references Q1/Q2. The underlying Q1/Q2 mapping is still recorded in this file's history if ever needed; the deck itself now optimizes for the simplest possible scan (1 through 5) over rubric traceability. Sequence unchanged: 1=language, 2=recognition-scope, 3=family-photo (live), 4=family-exceptions, 5=no-calendar (backup). This supersedes Decision 8's "small eyebrow tag naming which competition rubric question" line and the pitch-deck-narrative spec's "tagged Q1/Q2" language, both updated to match.

12. **Each insight slide is restructured into two labeled sections: 洞察 (observation) and 設計決策 (design decision).** With each slide now covering exactly one topic (Decision 8) and no longer competing for space with 4 others, there was a lot of unused vertical space, and the observation/decision were still running together as one undifferentiated paragraph — in several cases joined by a mid-paragraph `<br>` (e.g. Insight 1's "...聽得懂中文語音。<br>於是決定加入語音播放..."), which the user flagged as an unwanted forced line break. Split the reasoning — already implicitly two-part (a finding, then what was done about it) — into two `.insight-section` blocks, each with a `.panel-title` label ("洞察" / "設計決策", reusing the existing Persona-panel label style rather than inventing a new one) and a `.card insight-body` underneath. The two halves now live in separate sections instead of one span with a manual `<br>`, which resolves the line-break complaint as a side effect of the restructuring rather than a separate fix. `.insight-sections` uses the same `flex:1` + `justify-content:space-evenly` technique already used for the Proposal sheet and Evidence blocks, so the two sections fill the slide's available height evenly instead of leaving dead space below.
    - **Insight 1 additionally pulls its 3 statistics (65.9%, 28.5%, 96.57%) into individual stat cards**, reusing the Evidence slide's `.evidence-card`/`.evidence-stat`/`.evidence-label` classes at 3-across (new `.evidence-grid--cols-3` modifier, with its own smaller stat font size than the Evidence slide's 2-across cards, since 3 numbers need less width each) rather than leaving them embedded in a paragraph. The other 4 insight slides keep prose-only 洞察 sections — their supporting numbers (43.3%/40.0%) already got hero stat-card treatment on the Evidence slide itself, so repeating that treatment here would be redundant, and the user's stat-card request was specific to Insight 1.

13. **The "阿福管家 ahok" watermark is removed from every slide that had it.** `.slide-tag` (top-right of `.slide-head`) was reused for two different purposes: a literal "阿福管家 ahok" watermark (on Proposal, Evidence, and all 5 insight slides — 7 instances total) and slide-specific descriptive labels with unrelated content (JTBD's "服藥回診提醒 App", Design Goal's "服藥提醒 App", Design Guide's "高齡友善·...", IA's "共 13 個畫面..."). User asked specifically to remove the watermark; only the 7 literal "阿福管家 ahok" instances were deleted (the whole `<div class="slide-tag">...</div>` element, not just emptied) — the other 4 slide-tags, which carry real per-slide information rather than a repeated brand watermark, are untouched. `.slide-head`'s `justify-content:space-between` degrades gracefully to a single left-aligned block on the slides that lost their right-side element.

## Risks / Trade-offs

- [Risk] Citing specific statistics on the evidence slide invites scrutiny → attribute exactly the sources already cited in the underlying research notes; do not reword or recompute the numbers, and cite only the abbreviated public sources (see Decision 6), never the internal notes file.
- [Risk] A color/icon accent with no family-set physical counterpart to mirror could look arbitrary → default to no accent (neutral) when family hasn't indicated a matching physical color, rather than assigning one automatically.
- [Risk] The "two problems" framing is subtle and could land flat if rushed in a 7-minute talk → keep the two layers visually and textually separated (per the user's readability request) rather than compressed into one paragraph, so the distinction reads at a glance.
- [Trade-off] No real persistence means the family form's caption/color input is decorative, same as its existing fields — accepted, matches current scope and precedent.
- [Risk] Wrapping the Proposal slide's six items in one shared frame while removing their individual card shadows could make the core-hypothesis row's accent tint look weaker by comparison (less contrast against a plain sheet than it had against a page background) → check contrast against the sheet's background once implemented, not just against the old page background.
- [Risk] Splitting Insights & Decisions into 5 slides plus the existing Evidence slide grows the deck to 14 slides total, up from the original 9 → the cover's `data-target` indices and the counter's initial fallback text need re-deriving again (same class of fix already done once when Evidence was inserted); get the final slide count right before touching those two spots to avoid a second round of drift.
- [Risk] Reordering the deck moves Persona/JTBD/Design Goal/Design Guide/IA later without changing their own content or internal links → verify none of them assumed a specific slide index (e.g. via `data-target`) that the reorder would break.
- [Risk] The new cover `<h1>` ("記得清、看得懂、按得到") is a different character count than the original ("吃藥不漏、回診不忘") and `.cover h1` uses `white-space:nowrap` with a `clamp()` font size — check it doesn't overflow or force horizontal scroll on the cover slide once rendered.
